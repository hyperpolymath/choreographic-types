== Governance

=== Overview

This project is governed by the following principles and structures to
ensure transparent, inclusive, and effective decision-making.

=== Roles and Responsibilities

==== Maintainers

Maintainers are responsible for: - Reviewing and merging pull requests -
Managing releases and versioning - Ensuring code quality and standards -
Triaging issues and bug reports - Community engagement and support

==== Contributors

Contributors are expected to: - Follow the code of conduct - Submit
well-documented pull requests - Write tests for new functionality -
Maintain existing tests - Update documentation as needed

=== Decision Making

==== Minor Changes

* Can be made by any maintainer
* Include bug fixes, documentation updates, dependency updates

==== Major Changes

* Require discussion in issues or pull requests
* Include new features, architectural changes, API changes
* Need approval from at least 2 maintainers

==== Breaking Changes

* Require RFC (Request for Comments) process
* Need approval from majority of maintainers
* Must include migration guide

=== Commit and tag signing

Every commit and every tag in this repository is signed, and GitHub must
show it as *Verified*, or as *Partially verified* when a maintainer has
signed on behalf of a different author (the re-sign recipe under "Agents
and bots" produces exactly that). Both badges mean a verified signature;
what is never acceptable is *Unverified* or no badge at all. The server
enforces this through rulesets, never through a bypass: `Immutable-Tags` (active) rejects unsigned tags, and
`Require-Signed-Commits` on `main` rejects unsigned pushes once enabled.
It is disabled at the time of writing (2026-10-13); enable it as soon as
every maintainer's key below is registered, and do not add bypass actors
for bots.

==== What "Verified" needs

Two things, on the same GitHub account: the signing key is registered
under _Settings → SSH and GPG keys_ as a *Signing key* (not an
authentication key), and the commit's committer email is a verified email
of that account (the `@users.noreply.github.com` address counts). One
account and one key per person. A private key is never shared, and two
people never commit under one identity.

GitHub shows *Partially verified* instead of *Verified* when the signer
is not the author and the author has Vigilant mode on. The
`Require-Signed-Commits` rule accepts both badges, so no separate check
is needed: a commit signed by a maintainer for a bot author passes, and
an unsigned commit does not.

==== Set-up, once per person and machine

SSH signing is the house choice: no agent, no expiry, verified by GitHub
exactly like GPG.

[source,bash]
----
ssh-keygen -t ed25519 -f ~/.ssh/git-signing -C "you@verified-email.example"
git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/git-signing.pub
git config --global commit.gpgsign true
git config --global tag.gpgsign true
git config --global user.email "you@verified-email.example"
mkdir -p ~/.config/git
echo "you@verified-email.example $(cat ~/.ssh/git-signing.pub)" >> ~/.config/git/allowed_signers
git config --global gpg.ssh.allowedSignersFile ~/.config/git/allowed_signers
----

Then add the contents of `~/.ssh/git-signing.pub` to the account as a
Signing key, turn on *Vigilant mode* in the same settings page so any
unsigned commit shows as Unverified, and test with one commit on a scratch
branch before relying on it.

Two people on one machine: one clone directory per account, and an
`includeIf "gitdir:..."` block per directory in `~/.gitconfig` that sets
`user.email` and `user.signingkey`, so the wrong identity cannot sign.

==== Checking

`git log --show-signature` locally (needs the allowed-signers file above);
the Verified badge on GitHub; or the public API, where
`commit.verification.reason` reads `valid` for a good signature and
`unsigned` for none.

==== Agents and bots

* Claude Code cloud sessions sign automatically: SSH signatures with a key
  registered to the `claude` GitHub account, committer
  `Claude <noreply@anthropic.com>`. Measured on #25: every commit from the
  session reported `verified: true, reason: valid`.
* Squash and merge commits that GitHub creates are signed by GitHub.
* CodeRabbit's "commit to this branch" features (docstring generation,
  autofix) write unsigned commits through the API. Keep those features
  off (`.coderabbit.yaml` pins the docstring and unit-test generators off;
  Autofix is a dashboard setting), or have a maintainer re-sign the
  commits before merge:
  `git rebase --exec 'git commit --amend --no-edit' <base>` with signing
  configured re-signs each one and keeps the bot as author. Never grant a
  ruleset bypass to a bot instead.

=== Documentation convention

Prose that nothing checks is not documentation this repository relies on.
What counts, by language:

* *Agda.* The type signature is the specification; `PROOF-STATUS.adoc` is
  the documentation. Every name a PROVEN or TESTED row cites must be a
  definition, and the comment block directly above it (no blank line
  between) must carry the line `-- Ledger <ID>.` naming that row; a cited
  file carries the line in its header. `scripts/check-repository.mjs`
  enforces both directions, rejects a duplicate row ID, and rejects any
  comment or document naming a row the ledger does not have. Beyond the
  ledger line, a comment says only what the type cannot: the proof idea,
  which laws it uses, and what is deliberately not claimed. Lemmas the
  ledger does not cite need no comment.
* *Shell.* Each function has a header comment stating its inputs, side
  effects and exit codes. Nothing checks it; keep it short enough to stay
  true.
* *JavaScript.* JSDoc is prose and is not type-checked: checking it would
  need TypeScript and the Node typings fetched at run time, and the
  documentation guard is kept free of dependencies on purpose. Keep
  `@param` and `@returns` truthful or leave them out.

CodeRabbit is told this convention through `.coderabbit.yaml`
(`path_instructions`), so it reviews against it rather than asking for
docstrings.
